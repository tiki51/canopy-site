A **playbook** is a process you repeat, written down once: the roles, the ordered steps, who owns each one, and what "done" means for it. You write the playbook, the agents execute it, and you sign off.

When a run starts, one agent becomes its **lead** (the playbook file calls it the coordinator). The lead hands each step to its owners with the tools it already has (delegating, handing off, posting in the channel), and Canopy keeps track of where the run is. The state lives in Canopy, not in the agent's session, so a run survives compaction and restarts.

Use a playbook when the same kind of work (a feature, a bug fix, a release) should go the same way every time.

## The two starters

The seed step adds two playbooks. Both are led by `@project-manager`.

| Playbook | Steps | Waits for you |
|---|---|---|
| **feature-build** | Capture the request, propose 3 designs, technical design docs and their review, build with a test plan, test and code review, a design check of the result, and a final step that waits for your sign-off. `@designer`, `@frontend`, `@backend`, `@test` and `@reviewer` fill the roles. | You pick one of the three designs before anything is built, and sign off on the result at the end. |
| **bug-fix** | Triage, reproduce with a failing test, fix, verify, review, and your sign-off, with `@bugfix-team`. | You sign off on the fix at the end. |

In both, review steps can send work back: a code review that finds a problem reopens the build (or the fix), and a rejected design goes back to the designer. Rejecting the final sign-off sends the work back to the build (or the fix) too.

Playbooks are global to Canopy. A run happens in a channel, so it works in that channel's repository.

## Steps, approvals, and send-backs

Each step has:

- **Who does it**: one or more roles or agents (two or more work on the step in parallel), or *The lead does it*.
- **What should happen**: Markdown the lead reads when the run reaches the step.
- **Done when**: how the lead can tell the step is finished.
- Three switches:
  - **✋ Wait for my approval before moving on.** The run stops at this step until you answer its sign-off card. An agent can never skip it or jump past it.
  - **↩ If changes are requested, send it back to** an earlier step. When a review rejects the work, the run reopens that step and its owners pick it up again.
  - **⤼ The lead may skip this step.**

In the library's step strips and in the builder, ↩ marks a step that can send work back, ✓ one that waits for you, and ⤼ one that can be skipped.

## The library

**Playbooks** in the rail lists every playbook as a compact row: a star, the title and description, who does the steps, how many steps there are, when it last ran (or *● N running*), **Start**, and a **⋯** menu with **Edit**, **Duplicate**, **Export file**, **Disable** (**Enable** on a draft), and **Delete**.

- **Star** the playbooks you run most and they move to a **Starred** section at the top; the rest are under **Other playbooks**.
- **Filter playbooks** narrows the list by name, title, and description; **Esc** clears it.
- Click a row to open it in place: its steps as a strip, and the channels where it is running.
- Disabled playbooks, including agents' drafts, sit in a collapsed **Drafts** section. Agents can't see or run a draft until you enable it, and drafts can't be starred.

Enabled playbooks are listed in every agent's prompt; a disabled one can't be started.

**+ New playbook** offers three starts:

- **Copy a playbook**: pick one (starred ones are listed first, with a filter once there are more than five), and a disabled copy opens in the builder.
- **Start blank**: one empty step and default settings.
- **Describe it to an agent**: say how the work should go and pick who drafts it. Canopy posts your request in a DM with that agent, and the agent saves a disabled draft for you to review.

## The builder

The builder shows a whole playbook on one page.

<Shot name="playbook-builder" scale={1} alt="The Canopy playbook builder with the About card, settings, and a list of steps" caption="Edit the settings, then each step: who does it, what should happen, and when it's done." />

- **About**: the title, the short name agents know it by, and one sentence on when to use it.
- **Settings**: **Led by** (or *Choose when starting*), **Team**, **Nudge the lead** after a quiet step (30 minutes by default), **Ask when starting** (a hint for the brief), and **Roles**, each with the agent who fills it when no team member does.
- **Steps**, up to 20. Click one to open it.

**+ Add step** offers ready-made kinds: *Task for an agent*, *Parallel work*, *Review* (it sends work back to the step above), *Your sign-off*, and *Lead's step*. Drag a step by its ⋮⋮ grip to reorder it, or focus the grip and use Space and the arrow keys. Send-backs follow their steps through moves and show as rails beside the list.

Problems show as you go in a red banner, and **Save** (⌘S) stays disabled until there are none. A playbook you create is enabled as soon as it's saved; copies and agents' drafts start disabled.

Underneath, a playbook is one Markdown file with YAML frontmatter. **Edit file text**, in the builder's `⋯` menu, opens it for hand editing, and export and import use the same file:

```markdown
---
name: bug-fix
description: Reproduce, fix, verify, and review a reported bug with the bug-fix team, ending in user sign-off.
team: bugfix-team
coordinator: project-manager
steps:
  - id: fix
    title: Fix
    owner: [backend, frontend]
  - id: review
    title: Review
    owner: reviewer
    on_reject: fix
  - id: sign-off
    title: User sign-off
    owner: coordinator
    approval: user
    on_reject: fix
---
```

An optional `section:` in the frontmatter files each run's new channel under that [sidebar section](/canopy-site/docs/navigation/#sections).

## Start a run

- **Ask an agent**: "@project-manager run the bug-fix playbook: checkout button does nothing on Safari." The agent that starts a run leads it, in its current channel unless you ask for a new one ("…in a new channel called checkout-safari").
- **The start page**: **Start** on a row, or **Start a run** in the builder. Say what the run is about (optional, and you can drop, paste, or attach up to 10 files), where it runs, who leads it, and who does what. **What will happen** previews the steps.
- **In a channel**: **Playbook › Run…** under **Automation** in the channel's Details.
- **The composer**: `/playbook bug-fix [@lead] [brief]`, in the current channel.

**Runs in** offers a **New channel**, named from the brief (you can change the name, the repository, and the [section](/canopy-site/docs/navigation/#sections)), or an **Existing channel**, picked from the open channels by repository (one with a run in progress can't be picked). Files you add are posted with the brief as the run's first message, and the lead is pointed at them. With no brief, the lead starts from the playbook alone.

<Shot name="playbook-start" scale={1} alt="The playbook start page: an optional brief with one attached file, Runs in set to a new channel in a Payments section, Led by, Who does what, and the What will happen preview" caption="Say what the run is about, if you like, and where it runs." />

Canopy fills the roles (your choices first, then the team, then the playbook's defaults) and refuses to start when a role has nobody. Anyone on the roster who isn't in the channel joins it. One run can be in progress per channel, and a run keeps the text it started with, so editing a playbook never changes a run in progress.

A [GitHub watch](/canopy-site/docs/context/#watch-github) can also start a playbook for each new item, such as every failed CI run on `main`, each in a channel of its own.

## Follow a run

While a run is in progress the channel header shows its chip, and Details shows the brief, the roster, and every step with its owners, status, and result. **Reassign** changes the lead; **Cancel run** stops it.

<Shot name="playbook-run" scale={1} alt="A playbook run in a channel's Details: the roster and steps with their status" caption="Where the run is, who has each step, and what each step produced." />

Only the lead advances a run; each step's owners report through their delegations. The timeline records the run in compact lines: "started the bug-fix playbook · 6 steps", "bug-fix: Reproduce done → Fix", "the bug-fix playbook is complete". If a step goes quiet for longer than *Nudge the lead*, Canopy wakes the lead once to check on it.

## Sign off

When the run reaches a step that waits for you, the chip turns amber ("waiting for you"), the channel gets a *needs you* badge, and a sign-off card appears at the foot of the timeline with the step's result.

- **Accept** completes the step and moves the run on.
- **Reject** reopens the step, and the lead takes the run back to the step that fits.
- When the lead offers options (say, three designs), each has its own **Accept**, and **Reject all** replaces Reject.
- A note is optional on every answer and goes to the lead with it.

The held step in the run panel carries a compact copy of the card, whose buttons work the same. Agents can raise the same card outside a playbook; see [Sign-off cards](/canopy-site/docs/watching/#sign-off-cards).

If the run goes back before a step you approved, that step needs your approval again.

## Agent-written playbooks

An agent can draft a playbook with `canopy_playbook_save`. It is saved **disabled**, because an enabled playbook instructs every agent. A notice at the top of the library ("@agent drafted … for you to review") and **Review** on the draft's row open it in the builder, with **Enable playbook** and **Delete draft**.
